ENGINEERING PLAYBOOK 01 / 09 // LIFECYCLE

The 6-Step Feature Lifecycle

1. Pull Latest Main

Always start your work from the latest validated production state.

git switch main && git pull

2. Cut Feature Branch

Create a branch with the proper ticket and type prefix.

git switch -c feat/ZM-40-auth

3. Atomic Commits

Commit small, verifiable units using Conventional Commits.

git commit -m "feat: ..."

4. Push & Open PR

Push branch to GitHub and open a detailed Pull Request.

git push -u origin feat/...

5. Peer Review & CI

CI passes automated tests; peer reviews and approves diff.

1 Approval Required

6. Squash & Delete

Squash-merge into main and immediately delete feature branch.

git branch -d feat/...
ENGINEERING PLAYBOOK 02 / 09 // MODELS

Branching Models Compared

1. GitHub Flow

Zemen Default: Short-lived feature branches cut from main, verified via CI, peer-reviewed, and squash-merged to deploy.

Standard for SaaS & APIs

2. Trunk-Based

Developers merge small changes directly to main multiple times daily behind feature flags. Requires extensive automated test suites.

High-frequency delivery

3. GitFlow

Multiple long-lived branches (develop, release, hotfix, main). High merge overhead.

Avoid for cloud services
ENGINEERING PLAYBOOK 03 / 09 // TAXONOMY

Zemen Branch Taxonomy

All branches must follow: <type>/<ticket-id>-<short-desc>

  • feat/ New user feature or API endpoint
  • fix/ Defect correction for an existing feature
  • perf/ Performance optimization
  • refactor/ Internal restructuring without behavioral change
  • chore/ Tooling, dependency, or configuration updates
# Valid branch names:
git switch -c feat/ZM-204-payment-gateway
git switch -c fix/session-timeout-redirect
git switch -c refactor/cms-parser
git switch -c chore/upgrade-nextjs-15

# Invalid branch names:
# x fix
# x patch-1
# x updates-new
ENGINEERING PLAYBOOK 04 / 09 // COMMITS

Conventional Commits Specification

<type>(<optional-scope>): <imperative short description>

[optional detailed body explaining WHY, not WHAT]

[optional footer: Closes #123, BREAKING CHANGE: ...]
Compliant Commit Message:
feat(auth): add refresh token rotation
Prevents replay attacks by issuing single-use refresh tokens on each renewal.
Non-Compliant Commit Message:
fixed bugs and stuff
Provides zero context for bisect audits or automated release notes.
ENGINEERING PLAYBOOK 05 / 09 // REBASING

Updating Behind Branches with Rebase

While you worked on your branch, teammates merged 5 other PRs into main. How to update cleanly:

Recommended: Rebase on Main

# Fetch newest commits from GitHub
git fetch origin

# Replay your commits onto newest main
git rebase origin/main

Keeps git history 100% linear and clean. No messy "Merge branch main into..." commits cluttering history.

What Rebase Does Behind the Scenes:

  1. Temporarily sets your branch commits aside.
  2. Advances your branch base to match newest main.
  3. Replays your commits one by one on top.
ENGINEERING PLAYBOOK 06 / 09 // REVIEWS

Pull Request Review Criteria

Required in Every PR:

  1. Context & Problem: Why is this change necessary? Link the issue.
  2. Verification Steps: Explicit commands or steps to test locally.
  3. Visual Evidence: Screenshots or console output for UI changes.
  4. Constrained Scope: Keep diffs under 400 lines wherever practical.
## Description
Implements telebirr checkout callback verification.

## Testing Steps
1. Run `npm run dev`
2. Navigate to `/checkout/test`
3. Verify successful redirect to `/receipt`
ENGINEERING PLAYBOOK 07 / 09 // SQUASH

Why Zemen Defaults to "Squash and Merge"

On your feature branch, you might make 12 messy WIP commits: 

commit 1: WIP login
commit 2: fix syntax error
commit 3: forgot to import react
commit 4: still fixing typo
commit 5: ready for review
Squash and Merge condenses all 5 WIP commits into one clean, single commit on main: feat(auth): implement biometric login screen (#102).
